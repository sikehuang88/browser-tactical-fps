# ISSUE-2 [P0][安全] 客户端自建账号系统，可绕过鉴权且明文密码风险

## 问题

`client/src/ui/StartupCinematic.tsx` 新增了一套**完全跑在浏览器里**的注册/登录，作为进入游戏的入口。

```ts
const ACCOUNT_STORE_KEY = 'tactical-frontline.accounts'
type AccountRecord = { username: string; passwordHash: string }

// 登录校验（第 74-78 行）
if (authMode === 'login') {
  if (!existing || existing.passwordHash !== passwordHash) {
    setAuthError('账号或密码错误')
    return
  }
}

// 口令摘要（第 315-319 行）
async function hashPassword(password: string): Promise<string> {
  const bytes = new TextEncoder().encode(password)
  const digest = await crypto.subtle.digest('SHA-256', bytes)   // 无盐、单轮
  return Array.from(new Uint8Array(digest), (b) => b.toString(16).padStart(2, '0')).join('')
}

function writeAccounts(accounts: AccountRecord[]): void {
  localStorage.setItem(ACCOUNT_STORE_KEY, JSON.stringify(accounts))   // 明文落盘
}
```

### 三个独立缺陷

1. **鉴权可绕过**：登录判定在客户端完成。攻击者改写 `localStorage['tactical-frontline.accounts']`，或直接执行 `sessionStorage.setItem('tactical-frontline.session', '任意用户名')`，即可以任意身份进入。
2. **口令摘要不安全**：无盐、单轮 SHA-256，彩虹表可直接还原。而这是一个真实的 `<input type="password">` 输入框 —— 用户会复用真实密码，一旦 localStorage 被读取（XSS、共享设备、浏览器备份同步）即泄露。
3. **绕过了已有的正确实现**：后端 `backend/internal/auth/auth.go` 已有 HMAC-SHA256 短期令牌 + `POST /api/v1/auth/guest` + `requireAuth` 中间件，且工作正常。这套前端 auth 完全没有调用它。

代码中有 `// TODO(M3): Replace local prototype auth with the backend identity service.`，说明作者知情。但它当前是**进入游戏的唯一门禁**，且会诱导用户输入真实口令，不宜以 TODO 形式留存。

## 与项目契约的冲突

- `docs/requirements.md` §9：「客户端代码、WASM、协议视为可分析，**不在客户端保存核心秘密**」
- `docs/requirements.md` §14 发布阻断：「可复现 RCE / **鉴权绕过** / 提权」
- `docs/requirements.md` §5 AUTH-001~003：游客+正式账号；OAuth/OIDC 短期令牌可刷新吊销

## 建议

短期（本迭代内二选一）：

- **A（推荐）**：删除密码表单，改为调用已有的 `POST /api/v1/auth/guest`，令牌存内存 + `sessionStorage`，仅保留展示名输入。
- **B**：如果开场 CG 只是想要一个"仪式感"入口，那就把它降级为**纯展示**（点击继续），不收集口令、不做校验，等 M3 接真身份服务。

长期：按 AUTH-002 接 OAuth/OIDC，口令永不落客户端。

# ISSUE-5 [P1][正确性] 延迟补偿的 RTT 计算跨两个时钟相减，注释与实现不符

## 问题

`server/src/server.rs` `handle_inbound` 的 Ping 分支：

```rust
let now = now_ms();
// 服务器用自身时钟测量 RTT，不信任客户端上报值（防伪造 200ms 回溯）。
let rtt = now.wrapping_sub(client_sent_at_ms).min(200);
world.set_rtt(player_id, rtt);
```

注释声称「服务器用自身时钟测量 RTT，不信任客户端上报值」，但 `client_sent_at_ms` 恰恰**就是客户端上报的值** —— `connection.ts:112` 发的是 `Math.round(Date.now())`，即客户端墙钟。`now_ms()` 是服务器墙钟。两个不同机器的墙钟相减，得到的是 `单程延迟 + 时钟偏差`，既不是 RTT，也没有摆脱对客户端的信任。

该值直接决定命中回溯窗口（`combat.rs:256`）：

```rust
let lookback = ((shooter.rtt_ms as u64) * (tick_rate as u64) / 1000).min(MAX_LOOKBACK_TICKS);
let target_tick = tick.saturating_sub(lookback);
```

### 三个具体后果

1. **时钟偏差 → 恒定吃满回溯**：客户端时钟落后服务器 200ms 以上（未开 NTP 的机器偏差常在秒级）时，`now - sent > 200`，`.min(200)` 恒为 200ms，该玩家永久享受最大回溯（"拐角杀"优势）。
2. **时钟超前 → 同样吃满**：客户端时钟超前时 `wrapping_sub` 下溢为接近 `u32::MAX` 的巨值，`.min(200)` 仍然是 200ms。
3. **诚实客户端的回溯窗口减半**：旧实现是 `now.saturating_sub(client_sent_at_ms).saturating_mul(2)`，用 `×2` 从单程延迟估算 RTT；新实现删掉了 `×2`。对时钟同步良好的诚实玩家，回溯量直接砍半，高延迟下命中判定会退化。

### 讽刺之处：正确的值已经算好了但被丢弃

客户端 `connection.ts:147` 在收到 Pong 时用**同一个时钟**算出了真 RTT（无偏差问题）：

```ts
this.measuredRttMs = Math.max(0, Math.min(1000, Math.round(Date.now() - p.clientSentAtMs)))
```

并通过 `encodePing(Date.now(), this.measuredRttMs)` 发给服务器。服务器 `protocol.rs` 也解出来了 —— 然后在 `server.rs:384` 丢掉：

```rust
let (ts, _measured_rtt_ms) = decode_ping(&env.payload);
```

## 建议

正确做法是**服务器自己配对**，完全不依赖客户端时间戳：

1. 服务器维护每个玩家的 ping 序号 → 服务器发送时刻（`Instant`）映射；
2. Pong 回来时用 `sent_instant.elapsed()` 得到真 RTT（单一时钟，无偏差、不可伪造）；
3. 回溯量用 `rtt/2 + 客户端插值延迟`，并保留 `.min(200)` 上限（§6 要求 ≤200ms）。

过渡方案：沿用客户端上报的 `measured_rtt_ms`（它至少是同时钟测量的真 RTT），配合服务器侧合理性校验（与历史 RTT 的滑动窗口比对，突变则拒绝）—— 但这仍然信任客户端，只应作为临时措施。

同时请修正注释，当前注释与实现不符会误导后续维护者。

2. `SetMaxOpenConns(1)` 加注释说明这是 SQLite 写串行化的必要约束，并开启 WAL（`PRAGMA journal_mode=WAL`）+ `busy_timeout`，让读并发起来。

# ISSUE-7 [P2][正确性] `ClaimCheckIn` 发奖非幂等，迁移到 PostgreSQL 后会重复发奖

## 问题

`backend/internal/store/sqlite/sqlite.go:253` `ClaimCheckIn` 是「读 → 判断 → 无条件写」：

```go
err = tx.QueryRowContext(ctx, `SELECT last_date,streak FROM user_checkins WHERE user_id=?`, ...)
// ...
if lastDate == today {                      // ← 判断
    return store.CheckIn{CheckedIn: true, ...}, nil
}
// ...
reward := checkInReward(streak)
tx.ExecContext(ctx, `INSERT INTO user_checkins(...) ON CONFLICT(user_id) DO UPDATE SET ...`)   // ← 无条件写
tx.ExecContext(ctx, `UPDATE users SET credits=MIN(16000,credits+?) ... WHERE id=?`, reward, ...)  // ← 发钱
```

「读取后判断，再无条件写」之间没有任何数据库层保护。

## 当前是否可利用

**当前不可利用** —— `sqlite.New` 里的 `db.SetMaxOpenConns(1)` 把所有请求串行化了，两个并发签到不可能交错。

但这意味着**发奖的正确性依赖于连接池配置**，而不是依赖数据库约束。这是一个潜伏缺陷：

- ISSUE-6 提到迁移 PostgreSQL 是既定目标。PostgreSQL 默认 READ COMMITTED 隔离级别下，两个并发 `POST /api/v1/checkin` 会**都读到旧的 `last_date`**，都判定「今天没签到」，然后都执行 `UPDATE users SET credits=credits+reward` —— 双倍发奖。
- 一旦有人放宽 `SetMaxOpenConns`（性能调优时的自然动作），SQLite 下也会暴露。

## 同文件里已有正确写法

`ClaimTask`（第 198 行）就做对了 —— 条件更新 + 检查影响行数：

```go
result, err := tx.ExecContext(ctx,
    `UPDATE user_tasks SET claimed=1,updated_at=? WHERE user_id=? AND task_id=? AND claimed=0`, ...)
n, err := result.RowsAffected()
```

两处实现风格不一致。

## 与项目契约的冲突

- §14 **发布阻断**：「结算**重复发奖**」
- §10：「结算幂等键；段位/处罚/经济变更保留原因与前后值」

## 建议

把 `ClaimCheckIn` 改成同样的条件更新，让数据库而非连接池来保证互斥：

```go
res, err := tx.ExecContext(ctx, `
  INSERT INTO user_checkins(user_id,last_date,streak,updated_at) VALUES(?,?,?,?)
  ON CONFLICT(user_id) DO UPDATE SET last_date=excluded.last_date, streak=excluded.streak,
                                     updated_at=excluded.updated_at
  WHERE user_checkins.last_date <> excluded.last_date`,   // ← 关键：条件更新
  userID, today, streak, stamp(now.UTC()))
if n, _ := res.RowsAffected(); n == 0 {
    return alreadyCheckedInResult, nil   // 今日已签，不发奖
}
// 只有真正更新成功才发钱
```

并按 §10 补一张 `credit_ledger` 流水表（记录原因、变更前后值、幂等键），这是「经济变更可审计」的落地方式。
